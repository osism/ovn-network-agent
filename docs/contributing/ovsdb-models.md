# OVSDB models and the supported OVN range

The agent talks to the OVN Northbound and Southbound databases over OVSDB. The
Go structs that describe the tables it reads and writes are **generated** from
the OVN schemas checked into `schemas/` — they are not hand-written.

This page explains what is generated, which OVN versions the agent supports, and
how to regenerate the models when you bump a schema.

## What is generated

| Path | Contents |
|------|----------|
| `schemas/ovn-nb.ovsschema` | The OVN Northbound schema, verbatim from the OVN release below |
| `schemas/ovn-sb.ovsschema` | The OVN Southbound schema, verbatim from the same release |
| `internal/nbdb/` | Northbound models, generated by libovsdb's `modelgen` |
| `internal/sbdb/` | Southbound models, generated by `modelgen` |

`ovn.go` aliases the eight tables the agent actually uses onto the generated
types, so the rest of the code keeps the short names:

```go
type (
    SBPortBinding = sbdb.PortBinding
    SBChassis     = sbdb.Chassis

    NBNAT                      = nbdb.NAT
    NBLogicalRouter            = nbdb.LogicalRouter
    NBLogicalRouterPort        = nbdb.LogicalRouterPort
    NBLogicalRouterStaticRoute = nbdb.LogicalRouterStaticRoute
    NBStaticMACBinding         = nbdb.StaticMACBinding
    NBGatewayChassis           = nbdb.GatewayChassis
)
```

Do not edit anything under `internal/nbdb/` or `internal/sbdb/` by hand. CI runs
`make models-gen-check`, which regenerates and fails the build if the result
differs from what is committed.

## Schema provenance

| Database | Schema name | Schema version | OVN release |
|----------|-------------|----------------|-------------|
| Northbound | `OVN_Northbound` | `7.6.0` | OVN 24.09 |
| Southbound | `OVN_Southbound` | `20.37.0` | OVN 24.09 |

The schemas are the **minimum** supported OVN release (24.09), taken verbatim
from the [`branch-24.09`][ovn-2409] branch of the OVN repository — *not* the
newest release CI tests against. This is deliberate: libovsdb rejects a
connection when the client model names a column the server's schema lacks, so
the generated models must be a subset of the *oldest* server the agent
supports. Generating from a newer release would embed columns that older
servers do not have (e.g. `Port_Binding.mirror_port`, new in OVN 25.09) and
silently raise the floor to that release. Generating from the floor keeps the
models valid against every server from 24.09 up, including the 25.09 that CI
installs (Ubuntu Cloud Archive `cloud-archive:flamingo`, OpenStack 2025.2) for
the integration and E2E suites — extra columns on the newer server are ignored.

[ovn-2409]: https://github.com/ovn-org/ovn/tree/branch-24.09

## Supported OVN versions

**Tested against: OVN 25.09.** **Minimum: OVN 24.09.**

The floor is set by the columns the agent's models declare, because libovsdb
validates the client model against the server's schema when it connects — a
column the model names but the server lacks fails the connection outright, so
the model must fit inside the *oldest* server's schema. Two things keep the
floor at exactly 24.09:

- `NAT.match` and `NAT.priority` were added in **OVN 24.09**. The agent reads
  them, so anything older is genuinely unsupported: an older Northbound schema
  is rejected at connect time.
- The models are generated from the **24.09** schemas, not a newer release, so
  they carry only columns that exist as of 24.09. This is what holds the floor
  down: a model generated from 25.09 would also declare 25.09-only columns of
  those tables (`Port_Binding.mirror_port`, `Logical_Router_Static_Route`'s
  `selection_fields`) and reject every server older than 25.09, even though the
  agent never reads them.
- Only the **eight tables listed above** are registered in the client database
  models (`sbDatabaseModel` / `nbDatabaseModel` in `ovn.go`). The generated
  `FullDatabaseModel()` is deliberately *not* used: registering every table would
  widen connect-time validation to columns the agent never touches, so an
  unrelated OVN schema change could refuse the connection outright.

Running against a server *newer* than 24.09 needs nothing special — the extra
columns it exposes are ignored. You only regenerate the models (see below) to
raise the floor, and doing so is a user-visible support change.

::: tip Monitors project explicit columns
Registering a table is not the same as monitoring all of it. `sbMonitorTables()`
and `nbMonitorTables()` in `ovn.go` list, per table, exactly the columns the
agent consumes. This is required, not an optimisation: `Chassis.nb_cfg` is bumped
by `ovn-northd` on every processing round, so monitoring it would fire a cache
event — and therefore a state refresh — on a cadence unrelated to the agent's
inputs, storming the debounce loop on an otherwise idle cluster.
:::

## Regenerate the models

After changing anything under `schemas/`:

```bash
make models-gen        # regenerate internal/nbdb and internal/sbdb
make models-gen-check  # verify the committed output is up to date (what CI runs)
go build ./... && go test ./...
```

`go generate ./...` runs the same two `modelgen` invocations (anchored in
`modelgen.go`).

## Bump the supported OVN version

Raising the **Minimum** is the only reason to touch `schemas/`. The checked-in
schemas are the floor release, so bump them to the *new floor* — never to the
newest release you happen to test against, or you silently drop support for
every server between the old floor and that release.

1. Copy the new **floor** schemas over the checked-in ones. On a host running
   that OVN they are at `/usr/share/ovn/ovn-nb.ovsschema` and
   `/usr/share/ovn/ovn-sb.ovsschema`; otherwise take them from the matching
   branch of the [OVN repository](https://github.com/ovn-org/ovn).
2. Run `make models-gen`.
3. Build and run the unit tests. A renamed or retyped column shows up as a
   compile error at the call site — that is the point of aliasing the generated
   types rather than wrapping them. If the build fails because the agent reads a
   column the new floor dropped, the floor is too new — the agent cannot support
   it.
4. Raising the floor is a user-visible support change: say so in the commit
   message.
5. Update the provenance table on this page, and the OVN version stated in the
   [installation guide](../guides/installation) and the README.
6. Bump the OVN the test environments install (`test/integration/setup.sh` and
   `test/e2e/Dockerfile.central`) so CI keeps testing against the schemas that
   are committed.
7. Run the integration suite (`make test-integration`, needs Linux + root) — it
   connects the generated models to a real `ovsdb-server` and is the gate that
   proves the regenerated models still match a live OVN.
